# TICKET_PORTAL#12 - My Events Management

## Goal

Give authenticated `MANAGER` and `ADMIN` users a working "My events" management flow in `ticket-order-web`, showing events owned by the signed-in user and allowing draft edits, publishing, and unpublishing through the existing event-management API surface.

## Context

The backend and OpenAPI contract already expose owner-scoped event listing through `GET /events?scope=MINE`. The generated web client includes `EventsApi.listEvents`, and the contract defines `EventListScope.MINE`. The Java controller authorizes this scope for `MANAGER` and `ADMIN` users only, then calls `EventQueryUseCase.listOwnerEvents` with the current user's id.

The backend already exposes publish and unpublish behavior for manager/admin-owned events. This ticket should add an update-style draft edit API through `PATCH /events/{eventId}` before wiring the web edit form. The current OpenAPI source defines update as `PUT /events/{eventId}` with `operationId: updateEvent`; this ticket should replace or complement that with a generated `PATCH /events/{eventId}` operation so the web flow calls a partial/update endpoint rather than treating event edits like creation.

The existing web app already has a routed event creation flow for `MANAGER` and `ADMIN` users at `/events/create`. It does not yet provide a destination where those users can see, edit, publish, or unpublish their events after creation. A "My events" page should fill that gap while keeping event ownership semantics unchanged.

This page is not an admin-wide event catalog. The current backend returns events owned by the authenticated caller. Therefore an `ADMIN` sees admin-owned events only, not every manager's events.

## Scope

This ticket includes:

- Adding a real "My events" nav link for `MANAGER` and `ADMIN` users.
- Adding a routed `/events/mine` page guarded to `MANAGER` and `ADMIN`.
- Fetching events with `GET /events?scope=MINE`, using the generated OpenAPI client through a handwritten wrapper in `src/api/eventsClient.ts`.
- Rendering the owned events list with loading, error, empty, refresh, and paginated states.
- Showing event fields already present in `EventResponse`, including name, status, date, place/city, type, price/currency, image/video presence when available, and seat capacity details.
- Linking from the empty state to `/events/create` for users who need to create their first event.
- Adding a draft-event edit route.
- Adding a draft-event edit form by reusing the create-event form model and field components where practical.
- Adding a contract-first `PATCH /events/{eventId}` update endpoint and the matching API implementation when the existing contract does not already provide it.
- Adding a web client wrapper and mutation for `PATCH /events/{eventId}`.
- Restricting edit actions in the UI to events whose status is `DRAFT`.
- Adding publish controls for draft events.
- Adding unpublish controls for published events.
- Refreshing the owned-event list and event details after edit, publish, or unpublish actions.
- Adding unit tests and Playwright coverage for manager/admin access and customer/anonymous redirects.
- Updating the root and web changelogs.

This ticket does not include:

- Deleting events.
- Viewing every event across all managers/admins.
- Filtering by owner other than the authenticated user.
- Adding database changes.
- Deleting media without replacing it.
- Background cleanup of orphaned/old media objects; cleanup jobs belong in a separate future service/spec.

## Routing

- Add `/events/mine` as a child route under the existing app layout.
- Add `/events/mine/:eventId/edit` as a child route under the existing app layout.
- Lazy-load the `MyEventsPage` route component.
- Lazy-load the draft-event edit page/form component.
- Keep auth state owned by `App`.
- Guard both routes inline, matching the current `/events/create` pattern: render the page only when `currentUser.role` is `MANAGER` or `ADMIN`; otherwise redirect to `/`.
- Add "My events" to `navItemsByRole.ADMIN` and `navItemsByRole.MANAGER`.
- Render the nav item as a `react-router` `Link` to `/events/mine`.
- The edit route must verify the loaded event is editable before showing the form. If the event status is not `DRAFT`, show a non-editable state with a link back to `/events/mine`.

## API Integration

- Add `listMyEvents(query: PageQuery): Promise<EventListResponse>` to `src/api/eventsClient.ts`.
- Implement it by calling `eventsApi.listEvents({ scope: EventListScope.Mine, page, size })`, using the exact enum/member name generated by the OpenAPI TypeScript client.
- Add `useMyEventsQuery` in `src/features/events`, with a query key such as `['events', 'mine', page, size]`.
- Add or update the OpenAPI contract so draft event edits are represented by `PATCH /events/{eventId}`.
- Define the request schema as `PatchEventRequest`. Only fields persisted by the current `Event` domain may be patchable in this ticket: `name`, `date`, `place`, `type`, and `details`. Each patchable field is optional and nullable: omitted or explicit `null` means keep the existing value, while non-null values are compared and updated when different. Do not advertise `city`, `summary`, `price`, or `currency` as patchable until those values are persisted by the event domain.
- Generate the Java API contract and web client from the updated contract.
- Implement the Java API `PATCH /events/{eventId}` handler, preserving the existing ownership and draft-only update rules.
- Load the existing event record from the database before applying updates. The existing record is the source of truth for current scalar values, ownership, status, image URL, and video URL.
- Add `patchEvent(eventId, command)` or `updateEvent(eventId, command)` to `src/api/eventsClient.ts`, backed by the generated `PATCH /events/{eventId}` operation for scalar event fields and details.
- Keep image and video bytes on the existing media endpoints: image replacement uses the event image upload endpoint, and video replacement uses the presigned upload plus confirmation flow.
- Add `publishEvent(eventId)` and `unpublishEvent(eventId)` wrappers in `src/api/eventsClient.ts`, using CSRF handling consistent with other mutating event calls.
- Add `useUpdateEventMutation`, `usePublishEventMutation`, and `useUnpublishEventMutation` hooks under `src/features/events`.
- On successful update, publish, or unpublish, invalidate/refetch:
  - `['events', 'mine']` owned-event list queries;
  - `['events', 'detail', eventId, true]` authenticated event detail queries;
  - `['events', 'published']` public event list queries when publish/unpublish changes public visibility.
- Reuse `toEventUserMessage` for mapped failures.

## Update Semantics

- Treat `PATCH /events/{eventId}` as an update of the existing event record, not a create-like replacement flow.
- Fetch the existing event record from the database first, compare incoming editable values against it, and update only fields that changed.
- For PATCH request fields, omitted values and explicit `null` values both mean "keep the existing field." Clearing optional fields is not supported in this ticket.
- Non-null PATCH values are compared to the existing database value and persisted only when different.
- Preserve unchanged database columns exactly as they are.
- Preserve ownership and immutable identifiers; the edit form must never submit or alter `ownerId` or `eventId`.
- Validate and persist scalar event fields through the existing event update service path, keeping the draft-only rule in the backend as the source of truth.
- `PATCH /events/{eventId}` does not receive image or video bytes. Media replacement remains owned by the media endpoints.
- If media values are unchanged, do not write new objects to S3 and do not update the stored media URL columns.
- If the image changes, replace the image object/value in S3 and update the event image URL in the database.
- If the video changes, replace the video object/value in S3 and update the event video URL in the database.
- Before replacing image or video media, validate the candidate upload against the existing S3 object metadata. If the candidate media is the same as the object already stored in S3, skip replacement and preserve the existing database URL.
- Use S3 metadata peek/head-object support to read existing object metadata without downloading the existing image or video body.
- Use checksum comparison as the preferred media identity check. The UI should calculate SHA-256 for selected video files when the backend needs a candidate checksum for comparison.
- Video uploads in this ticket are expected to be short clips, up to 3 minutes and up to 100 MB. Validate that limit in the UI where practical before starting checksum/upload work, and enforce the same 100 MB limit on the backend when issuing and confirming video uploads.
- Store media comparison metadata alongside the S3 object when possible, including at least content length/size, content type, and SHA-256 checksum metadata.
- Use `sha256` as the canonical S3 custom metadata key, sent during upload as `x-amz-meta-sha256`, with a lowercase hex SHA-256 value.
- For video presigned uploads, require the UI-provided SHA-256 checksum in the presigned URL request. The backend must include the checksum, content length, and content type in the issued upload requirements/metadata so S3 stores the comparison fields. The generated `requiredHeaders` must include the checksum metadata header, and the UI must send returned required headers exactly.
- On video upload confirmation, perform S3 metadata peek/head-object validation and reject confirmation if the stored checksum, content length, or content type does not match the issued upload values, or if the stored size exceeds 100 MB.
- For image upload, prefer the simple backend-owned path: the backend receives image bytes, can calculate checksum from those bytes if needed, and stores comparison metadata with the object. Image checksum behavior is lower priority than video and should stay simple.
- If the event has no existing media URL, or if the referenced S3 object does not exist, upload the selected media and update the database URL.
- If the referenced S3 object exists but lacks checksum/metadata required for comparison, treat the selected media as changed, upload it to S3, and update the database URL.
- If both the candidate checksum and existing S3 checksum are available, compare those checksums. Matching checksums mean the media is unchanged; different checksums mean upload the candidate media and update the database URL.
- When a candidate video differs from the existing S3 object, replace the stored video; do not keep both active video values on the event.
- If media replacement succeeds but database persistence fails, the implementation must avoid leaving the event pointing at a stale or partial value. Prefer the existing storage-port recovery pattern if one exists; otherwise document the cleanup/rollback approach before implementation.
- Media replacement order is: upload and validate the new object, update the database URL, then best-effort delete the old object after successful persistence. If database persistence fails, best-effort delete the new object. If old object deletion fails after database success, log it without failing the user-visible update.
- Do not build background cleanup in this ticket. Orphaned/old media cleanup belongs to a separate background-task service/spec.

## UI / Component Design

- Page title: "My events".
- Keep the page practical and dense, matching the existing ticketing-product UI.
- Display a list/table hybrid that works on mobile and desktop:
  - event name and status;
  - date/time;
  - place and city;
  - type;
  - price/currency when present;
  - capacity details from `details.numberOfPlaces`, `details.numberOfRows`, and `details.seatsPerRow`;
  - media indicators when `imageUrl` or `videoUrl` exists.
- Provide a "Create event" action in the page header for `MANAGER` and `ADMIN`.
- Provide a refresh icon/button that refetches the query.
- Show an "Edit" action only for `DRAFT` events.
- Show a "Publish" action only for `DRAFT` events.
- Show an "Unpublish" action only for `PUBLISHED` events.
- Disable row-level actions while the corresponding mutation is in flight.
- Empty state copy should be short and action-oriented, with a link to create an event.
- Avoid shipping placeholder controls for analytics, orders, deletion, or non-draft editing.

## Draft Edit Form

- Reuse the create-event form shape, validation schema, field grouping, and reusable field components where practical so managers/admins do not learn a second form model.
- Extract shared create/edit form pieces only where reuse is real: for example an `EventForm` component plus create/update mapping helpers, rather than duplicating all field markup in two route pages.
- Load the event by id with the authenticated event detail endpoint before rendering editable fields.
- Render the form only when the loaded event status is `DRAFT`.
- Pre-fill fields from `EventResponse`, including details and optional place types when present.
- Submit the same normalized form values used by event creation to the event update wrapper/mutation, mapping them to the `PATCH /events/{eventId}` request body at the API boundary.
- Include image/video controls in the edit form. When a video file is selected, validate the 100 MB limit in the UI where practical and calculate SHA-256 before requesting the presigned upload URL, then call the existing video presigned upload flow instead of sending bytes through `PATCH /events/{eventId}`. Show a preparation/loading state such as "Preparing video..." and disable the relevant submit/upload controls while hashing or uploading. The backend media flow must compare the candidate checksum with S3 metadata when available before replacing stored media.
- On success, return to `/events/mine` or show an in-place success message and keep the updated form values. Prefer returning to `/events/mine` if the page is primarily list-driven.
- On failure, stay on the form and show the mapped API error.
- Do not allow changing event ownership.
- Do not support deleting media without replacement in this edit form.

## Accessibility

- Move focus to the page `<h1>` on route entry.
- Give the refresh and create actions clear accessible names.
- Give edit, publish, and unpublish controls clear accessible names that include the event name.
- Confirmation is not required for publish/unpublish unless future product guidance asks for it; visible in-flight and error states are required.
- For publish/unpublish failures, keep the error local to the affected event row, leave the visible status unchanged, and disable only that row's action while the mutation is pending.
- Use semantic list/table structure that remains readable on small screens.
- Use `aria-live="polite"` for loading/error/refresh status where appropriate.
- Ensure status text and event metadata do not overflow on mobile.

## Acceptance Criteria

1. `MANAGER` and `ADMIN` users can navigate to `/events/mine`.
2. The page fetches owned events through the existing `GET /events?scope=MINE` contract.
3. `CUSTOMER` and logged-out users cannot access the page.
4. The page handles loading, error, empty, refresh, and populated states.
5. Draft events expose edit and publish actions.
6. Published events expose unpublish actions and do not expose edit actions.
7. The draft edit route and form submit scalar/detail event updates through the configured PATCH endpoint.
8. The update flow fetches the existing database record, changes only values that differ from that record, and preserves unchanged database values.
9. PATCH omitted fields and explicit `null` fields preserve existing values; clearing optional fields is out of scope.
10. Changed image/video selections use the existing media endpoints and replace the corresponding S3 object/value only after checksum validation shows they differ from the existing S3 object. Missing existing S3 object or missing existing checksum metadata means upload the selected media and update the DB URL.
11. Existing S3 image/video metadata is read through metadata peek/head-object support without downloading the existing object body.
12. Video uploads are limited to 100 MB in this ticket, with UI validation and backend issuance/confirmation enforcement.
13. Video presigned upload and confirmation enforce checksum/content length/content type metadata using the `sha256`/`x-amz-meta-sha256` convention.
14. Image and video upload flows populate the S3 metadata required for future change detection.
15. Media replacement follows the defined ordering: upload/validate new object, update DB URL, best-effort delete old object; on DB failure, best-effort delete the new object.
16. Owned-event list and event details refresh after edit, publish, and unpublish actions.
17. Contract, generated-client, and Java API files are updated only as needed to add `PATCH /events/{eventId}`; no database files are changed.
18. New and existing web tests pass via `make test-web`.
